# マクロ評価 v2・式からの検査再開と診断改善

同じ27入力・同じルーブリックで前回 [r2](../20261109-macro-authoring-v2-r2/REPORT.md) と比較した。必須 **11/11** 成功、受理した13プログラムの16 export は Wasmtime／V8 の両方で期待値に一致した。探索課題の未達は4件から3件に減った。

## 変更と制約

マクロを展開した後、関数本体の先頭へ戻る処理を、影響を受けた式からの再開に変更した。完了した外側の式と先行する式を保持する。型を調べるための試行中は展開を外側へ戻し、仮の LocalId／LoopId を破棄して構文だけを再利用する。

新しいジェネリック実体が必要なら、型環境を無効化して全体検査を行う。関数完成時の展開後の構文検査と、最終的な型・effect・所有権・resource・race などの契約検査は残した。展開数512・検査200万ノードなどの予算は変更していない。ランタイムの変更はない。

追加の深い入れ子検査ではホストのスタックオーバーフローを発見した。再開位置の深さを含めて展開を検査し、通常の `let`・`block`・`if` の検査を大きな命令ディスパッチから分離した。60段のマクロが5重の block をそれぞれ生成する反例は、クラッシュせず `E_MACRO_LIMIT` を返す回帰テストになった。24段の同形式が成功することも別途確認した。これは、この反例に対する検査であり、任意の入力の終了性の証明ではない。

## 計測結果

| 単一関数の展開数 | 前回 check 中央値 | 今回 check 中央値 | 今回の結果 |
| --- | ---: | ---: | --- |
| 32 | 17.55ms | 6.58ms | 成功 |
| 128 | 203.10ms | 17.87ms | 成功 |
| 256 | 776.51ms | 35.22ms | 成功 |
| 512 | 1,343.09ms・予算超過 | 77.55ms | 成功 |

単一関数256展開はこの計測で約22倍速い。予算で数える構文ノード訪問は **1,317,396 → 9,751**、関数検査の開始回数は **257 → 1**、モジュール検査はどちらも1回。512展開では訪問19,479、関数検査1回だった。これらの訪問カウンタは、入力・再開した構文・完成した本体を走査する仕事量であり、全 checker 操作数ではない。

既存の分散256展開は35.72ms → 36.64ms、分散512展開は104.45ms → 95.80ms。こちらから一律の高速化は主張しない。各3回のCLI計測で、起動と読み込みを含む。今回の計測中は他の検査を走らせていないが、OS の負荷まで固定した計測ではない。複雑な推論で同じ包含式を再試行する場合は残る。

前回と今回の両方が受理した12プログラムは、Core Wasm の SHA-256 もすべて一致した。ゲストの実行速度を上げる変更ではなく、コンパイル時の検査の改善である。

## 残る3課題と診断

| 課題 | 診断の改善 | 意味の変更 |
| --- | --- | --- |
| 後続の初期化式から新しい束縛を参照 | 呼び出し元のスコープを説明し、外側の `%let` や明示的な依存の引き渡しを案内 | なし |
| Result 束縛の後ろに body を置く反復テンプレート | 不正な位置の `...` を指し、末尾反復または再帰ルールを案内 | なし |
| 委譲する body を block で包む | body 全体をそのまま転送し、ラッパーを委譲先の束縛スコープ内へ置くよう案内 | なし |

これらは現在の契約に沿った拒否として維持した。Result は今回の直接反復テンプレートが未対応という結果であり、別の再帰定義が不可能とは判断しない。初期化式の暗黙捕捉は追加していない。スコープの help は捕捉した束縛名との対応が確認できた場合だけ表示し、無関係な未定義名には付けない。
