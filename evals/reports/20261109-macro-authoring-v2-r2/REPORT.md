# マクロ作成・合成・規模の評価 v2

**必須11/11件が成功し、探索課題4件が未達**。受理された12プログラムの15 export の結果は、それぞれ Wasmtime と V8 の両方で期待値に一致した。受理後の誤動作は検出されなかった。

処理系を変更せず、現行の型推論・公開型情報API・束縛合成を使って17課題を試した。入力、期待値、ルーブリック、実装ハッシュを実行前に固定し、各課題を3回 check した。ABI 解放・取消し・エディタの回帰検査は、併走した [v1 r3](../20261109-macro-usability-v1-r3/REPORT.md) の20/20成功を参照する。v2 自体に新しい ABI／エディタ検査はない。

## 型引数を補う用途では通常関数で足りる

Option → Result の変換を、通常の `call $option.ok-or`、暗黙推論を使うマクロ、公開 `option.element` を使うマクロで比較した。

| 書き方 | 利用箇所のトークン | マクロ定義 | プログラム全体 | Core Wasm |
| --- | ---: | ---: | ---: | ---: |
| 通常関数 | 35 | 0 | 154 | 592B |
| 推論を使うマクロ | 34 | 17 | 170 | 592B |
| 型の射影を使うマクロ | 34 | 36 | 189 | 592B |

3成果物の SHA-256 は同一。成功42・失敗−7も両エンジンで一致した。公開型情報を使う書き方は内部の正規化構文に依存しないが、この用途だけなら通常関数が最小になる。トークン数だけで読みやすさや開発時間の優劣は判断しない。小さい課題の計測順は固定しており、数msの差から高速化も主張しない。

## 残った探索課題

| 課題 | 観測した拒否 | 現行仕様との関係 |
| --- | --- | --- |
| 後続の初期化式から先に導入した変数を参照 | `E_UNKNOWN_LOCAL` | `bind` が名前を公開する先は body。捕捉した初期化式は呼び出し元スコープで解釈する契約 |
| 反復した Result 束縛をテンプレートへ直接挿入 | `E_MACRO` | 試した `(%result.do (?name ?value) ... ?body)` は末尾以外の反復を使っている |
| 委譲先へ渡す body を `block` で包む | `E_MACRO_BINDING` | 契約が保証するのは body 全体の直接転送。再構成した束縛スコープは推定しない |
| 単一関数内に512展開を集中 | `E_MACRO_LIMIT` | 既存の200万ノード検査予算に到達。関数を分けた512展開は成功 |

最初の3件は現在の境界に沿った拒否であり、そのままコンパイラの不具合とは扱わない。初期化式が外側の同名変数を見る反例は期待値41となり、暗黙の捕捉が起きないことも確認した。組み込み `%let` グループの逐次スコープとは区別する。

Result の失敗は、この直接反復テンプレートについての結果。再帰的なマクロなど別定義で同じ利用構文を実現できるかは未評価であり、Result DSL 全体が実現不能とは結論しない。

診断では反復の位置、body 全体の転送、初期化式のスコープについて具体的な修正案が不足する。実装知識なしで拒否理由に到達しにくい点が、次の改善候補になる。

## 単一関数内の再検査が次の性能課題

| 展開数 | 単一関数 check 中央値 | 関数に分散 check 中央値 | 単一関数の結果 |
| --- | ---: | ---: | --- |
| 32 | 17.55ms | 5.97ms | 成功 |
| 128 | 203.10ms | 16.55ms | 成功 |
| 256 | 776.51ms | 35.72ms | 成功 |
| 512 | 1,343.09ms | 104.45ms | 予算超過で拒否 |

CLI 起動・読み込みを含む各3回の中央値。CPU時間やゲスト実行時間ではない。展開数をそろえて関数配置を変えた比較で、実行時の到達可能な関数数までそろえたベンチマークではない。

256展開の構文ノード訪問数は単一関数 **1,317,396**、分散 **9,498**。どちらもモジュール検査は1回。関数単位の再検査によって別関数を巻き込まなくなった一方、大きな同一関数の先頭からの検査は繰り返している。512失敗時の部分カウンタは公開されておらず、推測値は記録しない。

副次的に、256展開の Core Wasm は単一関数5,844B・分散99B。code section も3,722B対25Bであり、差は name section だけではない。単一関数のサンプルには結果を捨てるスカラー計算が多く、不要なローカルや式の削除を調べる材料になる。ただし実行時の処理内容は異なり、実行速度への効果は未計測。削除する場合も trap・例外・所有権の意味を維持する必要がある。

## ルーブリック

実装者本人による非盲検評価。各軸0〜4、平均点は出さない。v1 とは課題が違うため点差を比較しない。

| 軸 | 点 | 根拠 |
| --- | ---: | --- |
| 利用側の可読性 | 3 | 成功・失敗経路を追える。今回の型引数補助は通常関数が最小 |
| マクロ作成 | 3 | 型推論と公開射影で内部型パターンを避けられる。仕様参照は必要 |
| 合成 | 2 | 独立した反復束縛と直接委譲は成功。今回の3種類の追加合成には制約 |
| 静的保証 | 4 | 検査した範囲でスコープ・重複拒否・両エンジンの実行結果が一致。型等は併走v1も成功 |
| 診断・エディタ | 2 | 既存LSPは成功。新しい拒否ケースの help は具体性が不足 |
| コスト・規模 | 2 | 分散512は成功。同一関数512は予算超過、256でも再訪問が多い |

静的保証の4点は、この課題集合での判定であり、すべてのプログラムの正しさの証明ではない。独立読者の理解度や人間の作業時間は測っていない。

## 次の改善順

1. 関数内の検査済み式を再利用する。型環境やジェネリクスが変わる場合は依存関係を無効化し、最後のモジュール全体検査を維持する。検査予算を上げるだけでは解決しない。
2. マクロ診断に、末尾反復・body 全体の転送・初期化式の呼び出し元スコープを説明する具体的な help を追加する。
3. 副作用のないスカラーの不要な式・ローカルを削除できるか、意味を保存する対照ケースで調べる。
4. Result の再帰的な束縛マクロを別課題で評価してから、新しい構文の必要性を判断する。初期化式の暗黙捕捉は追加しない。
