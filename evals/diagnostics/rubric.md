# エラーメッセージ品質 v1

各ケースを5軸、各0〜4で評価する。まずコードと実際の診断から原因・修正案を答え、次に採点する。
0=情報なし/誤誘導、1=推測や実装探索が必要、2=おおむね分かるが重要な情報が不足、3=小さな確認で特定・修正できる、4=局所的に迷わず特定・修正できる。

| 軸 | 見るもの |
|---|---|
| location | 問題のファイル・行・列、必要なら定義/先行操作との関係を示すか。include元と実際のエラー箇所を区別するか |
| cause | 何がどの規則に違反したか、関係する識別子や操作が分かるか |
| expectation | 実際と期待する型・引数数・所有状態・effect等を区別するか。構文なら期待する構造/区切りを示すか |
| repair | 宣言された意図を保った修正が分かるか。検査や機能の削除を勧めず、別のエラーへ誘導しないか |
| focus | 主要な問題が見つけやすく、内部ID・panic・無関係な情報や二次エラーに埋もれないか |

目標は全ケースの全軸3以上。平均や総点で弱いケースを相殺しない。
拒否できたこと・修正後にコンパイルできたこと・モデルがコードだけで正答できたことを、メッセージ品質の加点には使わない。
根拠には診断の具体的な文言とソース行を示し、診断から分かった情報と、コード/チートシートから補った情報を分ける。
特定の全文・英語表現への一致は求めない。意味・位置・修正可能性を評価する。

機械検証は、元コードの拒否、panicがないこと、位置の妥当性と期待する行、正常対照、修正の型検査と非公開の振る舞いテストを確認する。
初見の読解役と修正役は別コンテキスト。正解・正常対照・非公開テスト・過去の点数を渡さない。親が説明を監査する。
基準とケースを改善途中で緩めない。変更するならsuiteのversionを上げ、同じ評価として点差を出さない。
