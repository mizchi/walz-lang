# チートシートと在庫台帳の初見評価

文法の概要は [CHEATSHEET.md](../../CHEATSHEET.md)。
型付きコア、GC、Option/Result/pair、所有値、固定マクロ、モジュール、実行方法を扱う。
この評価では言語仕様を追加せず、チートシートと [main.gwat](../../examples/apps/stock-ledger/main.gwat) の注釈を改善した。

## 手順と固定基準

[RUBRIC.md](RUBRIC.md) の20項目を最初の配布前に固定した。
G=構文、T=型の流れ、C=制御と終了、W=変更したプログラムの実行、D=資料の十分性を各4点で採点する。
重大条件を全て満たし、18/20以上を合格とする。

各ラウンドは会話履歴も過去の評価も渡さない新しい読解役・実装役の2エージェント。
読解役は配布資料だけ、実装役は同じ資料と CLI の check/types/fmt だけを使った。
実装課題は、在庫台帳と配送行数を pair の状態にして、main の成功値を0から配送行数へ変えるもの。
親が回答を採点し、候補を別プロセスでビルド・実行した。自己採点だけでは合否を決めていない。

全4候補の56チェックが成功した。第4回は資料不足の指摘なし。
第3回で2回連続合格・重大な新規誤読なし・未見課題正解を満たしたが、成功 payload の観測手順を補った後に第4回で追加確認した。
最終版でも同じ条件を満たし、固定した上限4回で評価を終えた。

1. **候補の起動手順が足りない → 実行方法を具体化。** 初回は型と制御の回答も変更コードも正しかったが、読解役が候補の入力付き実行まで再現できると判断できなかった。配布物に候補パス・作業ディレクトリ・build/text-cli のコマンドを追加した。result.let の裸の U の役割を表にし、サンプルにも T/U/E と unit 束縛の注釈を付けた。
2. **pair を Result で返す括弧が追いづらい → 実行できる短い例を追加。** 第2回の回答と実装は正解だった。資料不足とは区別し、独立した pair 状態の関数をチートシートへ追加した。関数・enum・Result の既存例と合わせ、4本をテストでコンパイル・実行する。
3. **CLI から成功値を観測できない → 既存 JS API の例を追加。** 第3回も合格し、未見の読解課題も正解だったが、text-cli は ok の payload を表示しない。runTextProgram が返す Result を stderr に表示する手順を追加した。実際にサンプルを実行して ok(14) と13行の JSON 出力を確認した。入力のコメント行も配送行数に含まれるため、出力行数とは異なる。

初回の自己採点指示には G/T/C/D の尺度の記載漏れがあり、読解役は -1（未採点）と返した。親は具体的な回答を元の固定基準で採点し、次回から指示に尺度も明記した。ルーブリック自体は変更していない。
親の verifier 初稿にも JSON のフィールド名の取り違えがあった。既存 expected.json と照合して訂正した後に全候補を検証・採点した。エージェントの不具合としては数えていない。

## 機械検証

各候補は同じ14チェックを受ける。配布物の SHA-256 照合、型・Wasm 検証、IR での pair 状態と初期化1回の確認、次の11実行例で構成する。

- 成功6例：空入力、空行とコメント、正常行と不正コマンドの混在、同じ台帳の再利用と末尾改行なし、在庫不足後の継続、Unicode と CRLF。成功の配送行数と JSON を照合する。
- 失敗3例：不正 UTF-8、入力の例外、出力の例外。同じ err code、入力の終了1回、後続出力の停止を確認する。
- 取消し2例：read 待ちと write 待ち。後始末の完了前に取消し確認が返らないことを確認する。

終了時に境界ハンドル表と ABI アロケータの live が0であることも確認する。GC ヒープ全体のリーク不存在の証明ではない。
検証プロセスは30秒で終了させる。Promise のタイムアウトだけでは停止できない同期 Wasm の無限ループにも対応する。

負例として元の成功値0の main を同じ verifier へ渡した。型と終了処理は通るが、行数5例と pair 状態の計6チェックだけが失敗することを確認した（[負例の結果](round-1/negative-control.json)）。
第3・4回には、err の result.let を drop した後に42を返す未見の例も出した。これは関数からの暗黙 return という誤解を検出するもの。[実行するモジュール](holdout.gwat) は42を返した。

型付きの読解回答は各 round-N の reader.json、実装時の診断は writer/report.json、親の実行結果は verification.json にある。
配送行数を返す [第4回の完成コード](round-4/writer/candidate.gwat) も保存した。

## 再現

`examples/gcwat` で実行する。Node v24.21.0、Cargo 1.98.0、Wasmtime 42.0.1 で検証した。

```sh
just test-cheatsheet
just grammar-eval-verify docs/grammar-eval/round-4
just check
```

配布資料、設問、回答、候補、親の採点、実行結果は round-N 配下に保存する。
配布時点のパス文字列は記録として維持している。上の verifier は渡されたディレクトリの候補を使うため、保存版の include もそのまま再実行できる。
新しい評価を準備する `just grammar-eval-prepare N` は既存のラウンドを上書きしない。エージェントの生成・採点を CLI が自動実行するわけではない。

## この結果から言える範囲

このサンプルの型、エラー経路、所有端点の終了を資料から理解し、小さな変更を実装できた。
最終チートシートは第4回の配布物と同じ SHA-256、4回のルーブリックも全て同じ SHA-256 であることを確認した。
長い型の反復と閉じ括弧の負担は残る。第3回の修正が示すように、満点は入力ミスがなくなることを意味しない。
同じモデルを使う少数の初見評価であり、人間全体への一般化や文法自体の優劣、作業時間の改善は検証していない。
