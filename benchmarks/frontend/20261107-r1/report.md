# Rustフロントエンドの計測 r1

標準型だけの利用では、型検査が590.3µsから20.6µs、Wasm生成までが586.5µsから35.1µsになった。
文字列を使う型検査も約1.90倍、JSONパーサーの型検査は約1.24倍になった。
大きいアプリのコンパイル全体への効果は小さい。在庫台帳は同等で、workflowの型検査にはばらつきが残る。
Cargo／rustcのビルド時間と、生成したWasmの実行時間は対象に含めていない。

## 変更

- 標準ライブラリの公開名と型エイリアスの範囲を、共有パーサーを使ってCargoのビルド時に索引化した。
- 実行時は静的な索引を二分探索し、使うライブラリとその依存だけを読み込む。
- 埋め込みライブラリの構文木を固定数の`OnceLock`に保持する。importの別名、名前衝突回避、型検査の状態は呼び出しごとに作る。
- 標準ライブラリの展開が不要な場合は、入力の構文木を再利用する。

型・effect・所有権の検査、最適化、Wasm validatorは引き続き実行する。
キャッシュにユーザーのソースや型検査済みIRは保存しない。埋め込みライブラリの構文木はプロセス終了まで保持するため、
反復回数に応じた蓄積はないが、初回の利用後には一定量のメモリが残る。

## 条件と結果

Apple M5 / arm64 / macOS 26.6.2、rustc 1.98.0、Criterion 0.8.2のbench profile。
同じ固定入力、依存関係、30サンプル、ウォームアップ500ms、目標計測時間2秒で変更前後を比較した。
APIの計測には結果の解放を含む。`cold-check`は毎回CLIを起動し、ファイル読み込みも含む。OSのファイルキャッシュは温まっている。

単位はµs。値はCriterionの推定値で、slopeがあればslope、なければmeanを各runについて選ぶ。
倍率は変更前÷変更後。95%信頼区間と丸める前の値は[report.json](report.json)に保存した。

`check/workflow`は最終runで平均5.0%増えたが、変化の95%区間は−0.94%〜+12.61%、p=0.21で、
Criterionは有意な差を検出していない。別のrunでは約11.66msだった。改善が安定しているとは判断しない。
`compile/stock-ledger`も最終比較では差を検出していない。
プロセス起動を含む`cold-check`では、API反復と比べて標準型の改善幅が小さい。

主比較は`before.log`と`final.log`および対応する生データを使った。
途中の`after.log`と台帳の再測定も保存した。追加の`confirm-*`は基準側を保存済み実行ファイルから直接起動しており、
主比較のCargo経由の起動と条件が異なる。基準値にも大きなばらつきがあったため、主比較の倍率には使っていない。

## プロファイルと正しさ

macOSの`sample`で標準型の型検査を5秒間採取した。変更前はメインスレッド4192サンプルのうち、
`standard::prepare`の部分木に2434サンプルあり、そのほぼ全部が構文解析だった。
標準型だけのimportで全ライブラリの公開名を調べるためにパースしていた処理が主な削減対象になった。
プロファイラー下の時間は上の速度比較に使っていない。

変更前の実行ファイルから、固定7入力の型付きIR・解析結果・WATと、型エラーの診断を保存した。
変更後もすべて一致し、別途生成した7入力のWasmもバイト単位で一致した。
不要なライブラリをパースしないテストは変更前に失敗することを確認した。
生成索引と元ソースの一致、並行チェック時の別名と名前衝突回避も検査している。

Rust 422件、Node 97件、Playwright 54件、eval 16件と、Criterionの17ケースのスモーク検査が成功した。
`just check`のfmt・Clippy・標準ライブラリ文書の整合性検査も通った。

## 記録と再測定

[capture.json](capture.json)に環境、コマンド、入力・ソース・実行ファイル・証拠ファイルのSHA-256を保存した。
[evidence.tar.gz](evidence.tar.gz)にはCriterionの変更前・変更後の生サンプルと推定値、
プロファイル、検査ログ、実装のスナップショットをまとめた。変更前の基準ファイルが最初のコピーと一致することも確認済み。
リポジトリのbase commitに加えて未コミットの先行する言語変更があるため、base commitだけではこの状態を表さない。

```sh
just test-frontend
just frontend-save next-before
# 変更して検査する
just frontend-compare next-before
```

新しい試行では別の基準名とrunディレクトリを使う。この記録と固定入力は上書きしない。
手順の詳細は[計測ガイド](../../../docs/frontend-performance.md)を参照。
