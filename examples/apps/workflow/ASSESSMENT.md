# 複雑な処理を実装した結果（2026-11-05）

これは初回実装の記録。現在のコードには後続の最適化を含む。[チューニング結果と変更前後の比較](TUNING.md)を参照。

依存グラフのワークフロープランナーを、既存の言語・ランタイムだけで実装できた。
本体892行、8ファイル。追加の型システム、マクロ、ランタイム API は不要だった。
静的なモジュール分割、opaque な可変 GC データ、enum の状態遷移、Result と Stream の終了処理を組み合わせても動作した。
今回の範囲では、新しい言語機能がなくて実装できない処理は見つからなかった。

## どこまで確認したか

- Wasmtime の言語内テスト12件、Rust の統合テスト2件。
- Core＋JSPI / Component とも、独立した参照実装と15入力群を照合。
- 240ジョブ・714回の依存登録に対する5通りのワーカー数、2,200ジョブのチェーン。
- ジョブ配列の8→4,096要素への拡張、65,536辺と各容量超過。
- ゼロ時間、同時完了、自己依存、循環の下流で停止するジョブ、再計画と計画後のグラフ更新。
- UTF-8 の途中で切れる入力、JSON の引用符・NUL等、I/O 失敗、読み書き中の取消し。
- 同じインスタンスを20回再利用し、状態の混入がないことと、ABI 割当て・所有 handle・scope 等が残らないこと。
- 表現への直接アクセスと、不正な pure 契約をコンパイラが拒否すること。

正常時の例は、5ジョブの計画を2ワーカーなら総時間12、1ワーカーなら15で出力する。
2,200ジョブのチェーンは時刻2,200,000,000、3回のネイティブ計算は合計6,600,000,000となり、i32 の折り返しを誤用していないことも確認した。

これはアプリケーションの正しさの形式証明ではない。配列添字・完了数・イベント時刻の不変条件は実装とテストで確認した。
GC ヒープの最大使用量や長期回収率、実際の OS ジョブ実行、最適なスケジュールは検証対象外。

## 計測で分かったこと

Node v24.21.0 の単発の観測。単位は ms。ビルド・instantiate を除き、同じテストの中で計測した。
Core の生成されたゲスト Wasm は17,041 byte（JS glue・linear memory 用モジュール等は別）。

| 処理 | Core＋JSPI | Component |
|---|---:|---:|
| 959入力行・240ジョブ・5計画・1,205出力行 | 26.8 | 2513.6 |
| 4,098入力行・ジョブ容量の境界 | 50.0 | 4711.8 |
| 4,400入力行・2,200ジョブのチェーン・2,201出力行 | 152.9 | 7858.1 |
| 65,795入力行・65,536辺と上限検査・1出力行 | 1331.6 | 77877.9 |
| I/O なし・2,200ジョブの構築とチェーン計画 | 100.9 | 107.5 |
| I/O なし・65,536辺の構築と上限検査 | 26.2 | 26.0 |

計算だけなら両バックエンドは近い。一方、text / Stream / ABI を経由する経路で Component に大きいコストが出た。
そのため通常の CLI は Core＋JSPI とし、大きい I/O 負荷は別の stress タスクにした。
I/O なしの版は ID 生成法も異なり、TSV 解析・JSON 出力を含まないため、差分を正確な ABI コストとは扱わない。
個別の関数や allocation の原因は、次に profiler で切り分ける必要がある。
実ファイルやネットワークの性能、統計的な速度差を測ったものではない。

## 書き心地と次の改善候補

1. **text の検索・分割・数値解析と JSON builder のライブラリ**。parse.gwat 179行と report.gwat 128行で、本体の約34%を占める。
   既存の concat / JSON escape だけでも書けるが、フィールド数が増えるほど束縛と連結が増える。言語の特殊構文を増やさず、型の閉じたライブラリでまず減らせる。
2. **Component の逐次 I/O 経路の計測・軽量化**。処理そのものと境界を通る経路を分けたところ、大きい差が確認できた。
   Stream の一要素ごとの処理、変換、task / resource 管理を profiler で調べる。Core の実行経路は既に利用できる。
3. **アプリケーションの ready queue / 入次数管理**。現実装は宣言順の未開始ジョブを繰り返し走査し、依存リストを調べる。
   境界 I/O を外しても2,200ジョブに約0.1秒かかる。大きいグラフを主用途にするなら、逆向きの依存辺と入次数、宣言順を保つ優先キューへ変更できる。これは言語機能不足ではなくアルゴリズムの選択。
4. **unit の結果宣言と S 式のスコープの診断**。実装中に (result unit) を書いて拒否された。unit を payload として書ける位置と、結果宣言を省略する位置の違いをチートシートへ追記した。
   また、括弧を1つ誤って namespace を閉じたときは unknown public func が先に出て、原因を追うために構造を確認した。括弧が対応していても意図したスコープと違う場合の説明には改善余地がある。

可変状態は Graph と Run に分離し、表現を隠した getter / 操作関数で扱えた。
配列と依存リストは用途別に定義したが、今回の規模では一般的な型引数や borrow を追加する必要はなかった。
再計画は別の Run を作るので、入力グラフや以前の結果を壊さず実装できた。
